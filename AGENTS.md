# stacks

## Overview

A bun workspace; every package is in `packages/<name>/`. `packages/cli` is `stacks`, the CLI: Effect 4 commands/services, doctor/version, lazy configuration, safe output and logs. Bun bundles the Node ESM package; Node 24 runs Vitest. `packages/format` (`@steamfield/stacks-format`) owns the portable entry, manifest, run-record and canonical bundle contracts. There is no vendor tooling; the one release tool is the maintainer's `bun run release`. The CLI has no network requirement except `update`'s one request to the npm registry and `submit`, which reaches GitHub only through `gh` and `git`. `packages/mcp` (`@steamfield/stacks-mcp`) is a placeholder with no code or scripts. The hosted API lives in a separate private repository, `stacks-api`. Code two packages share goes in its own package, never imported across another package's `src/`. How the monorepo works and how to add a package: README.md, "Monorepo".

The root owns the harness: `.claude/`, lefthook, CI, the root `biome.json`, `tsconfig.base.json`, and the root test suite in `tests/`: the hook tests in `tests/hooks/` and the delegate runner's in `tests/scripts/`. Each package owns its source, tests, `tsconfig.json` (extending `../../tsconfig.base.json`) and any Biome plugins in a nested `biome.json` (`"root": false, "extends": "//"`). See docs/harness.md.

## Test runs

Iterate on scoped tests: the test files or `-t` filter covering what you changed (`bun run test:unit tests/<file>.test.ts` in `packages/cli`, `bunx vitest run tests/<file>.test.ts` in `packages/format`), plus lint and typecheck. Run the full gate once, as the last check before handing back or committing, and again only after a change made to fix what it found. Never run the full gate or a whole suite to check work in progress: each run holds a host for minutes and delays every other agent's gate. A delegate runs no gate at all; Claude runs it once on the delegate's work after the refactor, and the command guard denies a delegate (`STACKS_DELEGATE=1`, set by `scripts/delegate.sh`) every whole-suite run, local or rr.

Several agents and delegates often work at once, and parallel gates on one laptop starve each other into timeouts. A clone that has test hosts runs the full gate and whole test suites through [rr](https://github.com/rileyhilliard/rr): `.rr.yaml` runs the task on the first free host (the dev machine in place, or a synced remote) under a per-host lock, so concurrent runs queue. All worktrees share one remote copy per host.

rr is opt-in per clone and off by default: `git config stacks.rr true` turns it on (stored in the clone's `.git/config`, so every worktree of the clone shares it and nothing is committed), and `git config --unset stacks.rr` turns it off. Check with `git config --get stacks.rr`. Opted in, the command guard denies local whole-suite runs and names the rr task; opted out, run the `bun run` commands above. "The gate" in contracts and skills means `rr check` in an opted-in clone and `bun run check` otherwise.

| Command (repo root) | Runs |
| --- | --- |
| `rr check` | The full gate, partitioned across the hosts (about 30 s) |
| `rr check-serial` | The full gate in order on one host (`bun run check`, as CI runs it) |
| `rr test` | Root tests, then every package's tests |
| `rr test-cli tests/<file>.test.ts` | CLI Vitest tests, optionally narrowed (`rr test-cli -- -t "<name>"`) |
| `rr test-hooks` | Root tests only |
| `rr e2e` | Pack and run the installed-package e2e tests |

Output is rr's JSON phase events on stderr, then the command's own output, then a `result` event whose `details.summary` has the test counts and `details.log_file` the full log; the exit code is the command's. `rr check` prints nothing on stdout: its `result` event lists `passed`/`total` partitions, each failed partition's host, `log_file` and parsed failures, and `details.log_dir`, which holds one log per partition. Read the counts as `.claude/rules/cli/verification.md` asks. rr needs its hosts in `~/.rr/config.yaml` and a reachable SSH agent. If `rr` isn't installed, or it fails before running the command (exit 1 with an error envelope such as `SSH_AUTH_FAILED` or `HOST_NOT_FOUND`), say so and run the same `bun run` command locally; never report a local run as an rr run. A single scoped test file, lint and typecheck are cheap enough to run locally.

In Claude Code, the session-start hook exports macOS's own ssh-agent socket for an opted-in clone, because the Bash sandbox can't reach every agent socket a session inherits; rr then runs inside the sandbox. A session started before opting in picks it up on its next start or `/clear`.

## Architecture map (packages/cli)

Paths below are relative to `packages/cli/`.

- `src/bin.ts`: Node/platform/Host/writer boundary, the bundled-registry filename adapter, the per-invocation `Foreground` holder, signal policy wiring and exit status.
- `src/main.ts`: one invocation, framework Console capture, safe outcome and logging.
- `src/cli.ts`, `commands/doctor.ts`, `commands/guide.ts`, `commands/list.ts`, `commands/new.ts`, `commands/add.ts`, `commands/validate.ts`, `commands/verify.ts`, `commands/skill.ts`, `commands/create.ts`, `commands/search.ts`, `commands/show.ts`, `commands/update.ts`, `commands/telemetry.ts`: real Effect command tree and thin handlers. `commands/runs.ts` reports project run history. `commands/schema.ts` prints the JSON Schema of each `--json` result, the error envelope and verify's events, from `core/result-schemas.ts::RESULT_SCHEMAS` (`jsonSchema`). `commands/root.ts::root` is the root with its shared `--json` flag, which a handler reads with `yield* root`; the root with no subcommand prints the agent guide.
- `src/commands/handoff.ts`: `projectFlags`, `prepareHandoff` and `completeHandoff` own the shared flag parsing, handoff preferences, result presentation and interactive launch flow for `new` and `add`; previews force a printed plan.
- `src/project-layout.ts`: the one owner of `.stacks/` paths and starter metadata text, imported by writers, readers, schemas and reports.
- `src/core/handoff.ts`: `decideHandoff` (pure: `inside-agent`, `launch`, `choose` or `print`, first matching rule wins; an untrusted entry never reaches `launch` or `choose`), `agentPrompt`, `LAUNCH_ARGS` (terminal and app launchers keyed by `Harness`), `LAUNCH_ORDER`, `launchDecision`, `handoffRecord` (Copilot to `other`, Codex app to `codex`, pending choice to `print`), picker text and `renderHandoff`. `new` and `add` decide before writing; `commands/handoff.ts` flushes the summary before a numbered `Terminal.readLine` picker when several unconfigured harnesses are found, records the choice, and launches through `Processes.interactive` or `Processes.exec` for the macOS app. `src/core/guide.ts`: the agent guide text (`guideText`, also `stacks guide`), `guideCommands` and the root `--help` footer (`helpFooter`, appended by `main`).
- `src/telemetry/`: `Telemetry` (`index.ts`) records `TelemetryEventV3` events (`events.ts`) into a spool under `Paths.state` and posts them to `<url>/v1/events` (`client.ts`). `consent.ts::consent` decides in order: `--no-telemetry`, offline, `DO_NOT_TRACK`, `STACKS_TELEMETRY_DISABLED`, settings, CI, `source_build`, `no_endpoint`, `not_notified`, `enabled`. The endpoint is `STACKS_TELEMETRY_URL` or the official URL, which `bin.ts` passes only in a build made with `STACKS_PUBLISH_TELEMETRY=1` (`scripts/release.ts`); every other build reports `no_endpoint`. The notice run sends nothing, but `new` and `add` on it store a deferred scaffold and the project link, delivered on the first enabled run. The verify event carries `asked` from `core/runs.ts::countAsked`. `new`, `add` and `verify` flush themselves; every other noticed command flushes once its output is written (`main` calls `flushAfterOutput`).
- `src/core/doctor.ts`: platform-free diagnostic program. Reports both bundled asset directories from Host.
- `src/core/remote-index.ts`: `RemoteIndex.current`, `bundle`, `status` and `layer({ keys, officialUrl })` own the signed remote origin's 24-hour cache, 1,500 ms deadline and persisted request backoff. Bin supplies no official URL until a host exists; without one or `STACKS_INDEX_URL`, the origin is off and status has `url: null`. `core/remote-index/verification.ts` checks signatures and compatibility; `files.ts` checks canonical directory digests and extracts verified data. `core/registry/remote.ts` merges the index below project/user and above bundled entries, preserves same-digest bundled identity and carries pinned default fragments into composition. `Registry.catalog` exposes names and tags without downloading bundles; `Registry.get` resolves and caches only the requested entry and pins, while `all` resolves the full listing. Loading reads each entry's directory and markdown file only; the deep symlink walk of an entry's tree is a per-entry check cached in the layer, run by `get`, `files`, `tree`, `read`, `bytes` and, for every entry, `all`. So `catalog`'s `rejected` is preliminary: a caller reports an entry as usable only after `get` or `all`. `Registry.bundled` is the bundled-only lookup `show` compares run evidence against. `schemas/remote-index.ts::RemoteStatus` is doctor's cache status; neither doctor nor verify refreshes the index. `core/allowlist.ts::Allowlist` fetches the signed dependency allowlist from `AppConfig.apiUrl` through `core/cached-fetch.ts`: `refresh` on `list`, `show` and `new`, `cached` (no request) for `verify`; failures are silent. `core/deps.ts::readDependencies` reads root manifest names and installed majors without running project code.
- `src/core/stats.ts`: `Stats.summary` and `detail` fetch published metrics through the shared cached fetch, with one state file per resource; `list` and `show` use them only for bundled or index entries, and `core/stats-text.ts::statsLine` is the one `Stats:` line both print. Bin passes the hosted API URL (`bin.ts::DEFAULT_API_URL`) as `Build.defaultApiUrl`; source builds and tests use `config.ts::SOURCE_BUILD` and accept a loopback `STACKS_DEV_API_URL`.
- `src/core/skill.ts`: `SKILL_WORDS` (a `SKILL.md` budget per skill), `installSkill` (every file of `skills/<name>/`, user/project targets, per-file compare and safe write); `src/schemas/skill.ts::SkillResult` is the install result. `skills/` is the skills root, resolved by bin as `Host.skill` beside the registry: `skills/stacks/SKILL.md` is the agent skill and `skills/stacks-author/` (`SKILL.md` plus `references/`) the authoring skill, which `src/core/guide.ts::authorGuide` prints as `guide author [topic]`. `plugin/` is the Claude Code plugin carrying committed copies of both, listed by the root `.claude-plugin/marketplace.json` pinned to the release tag (`packages/cli/docs/maintaining.md`, "Publishing the Claude Code plugin").

## Conventions

Use namespaced Context.Service classes, static layer factories and fresh per-invocation state. No globals/caches across runs. Core uses Effect FileSystem/Path and remains unchanged under Node. Only bin/explicit adapters may use Bun; only `bin.ts` and `src/platform/` use Node process APIs (`process.kill`/`on`/`exit`, `node:child_process`, `@effect/platform-node`); everything else runs processes through `Processes`. Only config reads env: a child's whole environment comes from `AppConfig.childEnv` (nothing inherited), and `Processes.which` is the only PATH search, over the captured PATH. No direct console or stdout writes in application logic. Output has three audiences, resolved once per invocation by `services/output.ts::resolveAudience`: `json` with `--json`, `human` only when stdout is a terminal, `AppConfig.agent` is `"none"` and `CI` is unset, `agent` otherwise (the default: an agent's shell, a pipe, CI). Audiences never behave differently; commands only render by `Output.audience`, and agent text drops what an agent doesn't need (rules/cli/cli.md, "Three audiences"). Grit and adapter guards enforce platform/schema/env/output boundaries. `core/` and `services/` never import `platform/` or `commands/` (one allowance: `services/processes.ts` imports `platform/process.ts`) and use no Node builtins except `node:crypto` for digests (`manifest.ts`, `fingerprint.ts`, `search/digest.ts`), `node:util` in `services/output.ts` and `node:fs/promises` for the writer's atomic `rmdir` (`scaffold/write.ts`, since Effect's `FileSystem.remove` can't remove only an empty directory). The root `biome-plugins/no-cross-package-imports.grit` rejects imports into another workspace package's `src/`, `scripts/` or `tests/` and its private subpaths; computed `import()` specifiers aren't checked.

Strict TypeScript 7: unchecked indices, verbatim modules, erasable syntax, explicit Bun/Node types and no emit. Biome: two spaces, double quotes, width 100, recommended rules and explicit type imports/exports. Structure rules are errors: cognitive complexity at most 15 per function, no nested ternaries, at most four parameters (pass an options object); only the registry's shipped files are exempt. Split an over-limit function into named steps rather than suppressing the rule. Prefer current patterns and dependencies; keep changes scoped.

## Code structure

Lint catches size; these are the placement mistakes it can't, each found in review here, with the fix.

- A fallback beside a service field. A default path or value computed next to a `Host` or config field (from `import.meta.url`, say) hides a missing input and breaks in the packaged bundle. Make the field required, set it in `bin.ts`, and give tests their value in `tests/helpers/cli.ts`.
- A shared helper left in its first user's module. When a second command needs a helper from `commands/new.ts`, move it to the module named for its concept (as `commands/handoff.ts` holds the flow `new` and `add` share), not an import from the other command.
- A growing `Effect.gen` body. A new case gets a named step (a function returning an Effect, or a small pure function) called from the body, not another branch inline. The body reads as the command's sequence of steps.
- Registry-wide work on a per-entry path. A command that needs one entry or composition reads and checks only that one; whole-registry passes belong to `validate` of a registry and to tests. Ask how the cost grows with the registry.
- Options nobody asked for. A parameter, flag or abstraction with one caller and no plan behind it is removed, not documented.
- A wide function signature. More than four parameters, or several of the same type in a row, becomes one options object with named fields.

## Error handling

Fixed safe tagged messages; `errors.ts::errorTable` is the one exit/retryable/keepsResult table, and `errorClasses` lists every class (a test keeps the two equal). Adding a tag means its class in `errorClasses` and its row in `errorTable`. Expected usage/input/not-found exit 2, config 3, upstream 4, VerifyFailed/VerifyChanged 5 (read the verify report), permissions 6, interruption 130, defects 1; BrokenPipe is quiet 0. The one exit outside the table: after `new` launches an agent, the invocation exits with the agent's status (`Invocation.exitWith`, applied only when the command succeeded, so no envelope). `--json`, a detected agent, a non-terminal and any untrusted entry never launch. main observes failures/defects once and clears stdout on error, except for a keeps-result tag (VerifyFailed, VerifyChanged, ValidationFailed), whose buffered result is flushed to stdout before the envelope. BrokenPipe rule: a closed stdout or stderr while writing the result or envelope is quiet and exits 0, except after a keeps-result tag, which keeps its own exit. The outer runtime maps a pending interrupt after cleanup to 130. `SpawnFailed` (`kind`: cwd, shell, command, resources; `errno`) is internal and outside `AppError`, so it is a Defect unless the caller handles it; a missing command under `/bin/sh -c` is a normal exit 127. Logs never serialize arbitrary cause objects or secrets; a defect is logged as its class and stack frames, without its message. Defects are not retryable.

Signals (`platform/signals.ts`): with no interactive child, SIGINT, SIGTERM and SIGHUP interrupt (finalizers run, exit 130). A second one within 1 s of the first is the same Ctrl+C delivered twice (terminal plus a forwarding wrapper) and is ignored; one 1 s or more later SIGKILLs every registered process group and exits 130 at once. SIGQUIT keeps its default action after the groups are SIGKILLed. While `Processes.interactive` runs a child, SIGINT and SIGQUIT are ignored (the terminal already gave them to the child) and SIGTERM and SIGHUP are forwarded to it. Process groups from `run`, `start` and `exec` get SIGTERM, 5 s, then SIGKILL on interruption, timeout or scope close; `run` and `exec` drain output for 2 s after exit before killing the group (`Finished.pipesHeld`). A SIGINT within 1 s of one left to the interactive child is still that child's Ctrl+C (a wrapper's late copy), and a SIGTERM or SIGHUP forwarded to the child stops the CLI with 130 once the child exits. Process groups leave the `Foreground` registry once seen gone and only registered groups are signaled. A closing scope sends SIGTERM to all of its groups at once, so they share one grace period. A `process.on("exit")` handler SIGKILLs any group still registered.

A tag may carry an optional closed `details` struct (`Schema.optionalKey` on its TaggedError fields), holding only CLI-produced values or caller arguments. Construction drops keys the schema doesn't name; `Output.error` encodes details per tag (`errors.ts::encodeDetails`) with `onExcessProperty: "error"`, so only a details object mutated after construction can reach the Defect path (exit 1). Details go only in the envelope, `{ error: { tag, message, retryable, next?, details? } }` (`errors.ts::ErrorEnvelope`, printed by `stacks schema error`); human and agent output print the message, then the lines `errors.ts::failureGuide` picks, indented, then `Next:` with the same text as the envelope's `next`. Every tag but BrokenPipe has a next action; a keeps-result tag's report carries its own `Next:` line, so text modes don't repeat it. Details never enter the message or a log record. An unknown subcommand is `Usage` with `details: { command, suggestions }` from `core/suggest.ts::closest`; effect/cli's own suggestions are discarded. An unknown flag is `Usage` with closed `details: { flag, command, suggestions }`, preserving the parser's flag spelling and command path (root: `stacks`). Suggestions use `closest` over that command's visible flags, including shared and built-in flags; remaining slots may name close positional arguments as `<name> (positional argument)`, up to three suggestions total. Text modes print the flag, command and suggestions, then `Next: run stacks <command> --help to list the flags and arguments.` (root: `stacks --help`). A parser-rejected value or missing argument is `Usage` with closed `details: { flag, value, expected, command?, suggestions? }`: the input's flag or argument name, rejected value, parser expectation and command path (root: `stacks`). Suggestions use `closest` over literal choices, `AgentId.literals` for agent values or `Harness.literals` for launch values. Text modes show the details and end with a `Next:` line naming that command's help (`stacks search --help`, for example). A keeps-result failure whose result couldn't be written (non-EPIPE) keeps its exit, and the command log record gets `result: "unwritten"` with the write error's tag.

JSON commands produce one result; JSON failures produce one stderr error envelope as the last stderr line. To preserve that contract, and to keep an agent's stderr to the failure itself, JSON-mode and agent-mode ancillary logs use only the configured JSONL file (none when `STACKS_LOG_FILE` is unset). Only human mode writes log lines to stderr, flushed before the result or error; `main`'s summary `command` record of an expected failure goes to the file only, so `Next:` ends stderr, while a Defect's stays with its stack frames. `Output.progress` writes live lines to stderr in human mode only, swallows every write error and stops after the first. `Output.event` is the one exception to a quiet stderr: in JSON mode it writes one JSON line per event (verify's `step-started` and `step-finished`, `schemas/verify.ts::VerifyEvent`, `stacks schema verify-event`), in agent mode an optional short line (`> <step>` as each verify step starts), in human mode nothing; it shares `progress`'s write-error policy, and the envelope stays the last stderr line. `Output.flushNow` (human and agent modes) writes buffered results immediately; once it has run, stdout is no longer empty on a later failure in that invocation. Only human output gets status colors (`Output.style`), scoped stderr redraws (`Output.live`) and terminal-width wrapping. Nonempty `NO_COLOR` disables color and redraws; `FORCE_COLOR=1` enables color only for humans, with `NO_COLOR` taking precedence. Output checks each stream's terminal flag separately. `Host.stdinIsTTY`/`stdoutIsTTY`, `stderrIsTTY`, `columns` and `stringWidth` come from bin.ts; core never reads the streams.

## Delegates

Claude Code orchestrates; Codex takes the coding tasks Claude delegates (`scripts/delegate.sh`, workflow in `.claude/skills/delegate/SKILL.md`). A delegate is trusted like Claude Code and works in its own worktree from a contract file with full access (network, `bun add`, git). It leaves its changes uncommitted and doesn't push, because Claude reviews, refactors and commits them, and it keeps to the contract's scope. A dependency it adds keeps shared versions in the root `workspaces.catalog`. Of the Claude hooks, only the command guards run for a delegate (`.codex/hooks.json` wires `.claude/hooks/guard-commands.ts` and `.claude/hooks/block-destructive.sh` for Codex's Bash tool; Codex reads it from the main checkout, so it lands there before it applies). The lint, typecheck and boundary hooks don't, so a delegate runs the contract's checks itself (`bun run lint`, `bun run typecheck` and the named tests; no gate, "Test runs") and reports each result; Claude reviews, refactors and commits. `.claude/rules/` is Claude's: a contract names the rule files that apply to the task. Before handing back, a delegate runs one review in a fresh Codex process with `.claude/agents/code-reviewer.md` as its prompt.
