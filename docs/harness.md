# Agent development harness

AGENTS.md is the project map. Path-scoped rules explain local conventions; skills hold checked reference material. Hooks give immediate feedback, lint enforces syntax and boundaries, tests prove behavior, and the project check command is the final local gate. CI runs those same project commands.

The shared TypeScript hooks use node APIs and run under Bun. `_lib.ts` handles payloads, process timeouts, project paths, and protocol output; `_shell.ts` parses shell commands so quoted examples and comments are not mistaken for execution. Generated-output guards protect tool-owned files; stack and application guards own their additional boundaries. Missing tools and advisory timeouts remain quiet.

`/test` scopes feedback before the full test command. `/check` runs the complete gate. `/feature` records a design, reviews it, implements and verifies in an isolated worktree, and hands off a reviewed PR. The architect agent is read-only; code review uses the `code-reviewer` agent (`.claude/agents/code-reviewer.md`), which extends `ce:code-reviewer` with this repo's checks. Use documented development commands, inspect on-disk logs, and terminate only processes you started. Keep secrets out of commands and logs.

To inspect the harness, read `.claude/settings.json`, confirm each wired file exists once, then run the shipped hook tests through the project test command. Test guards with a deny and a near miss; test advisory hooks with a realistic temporary project. Never treat a hook as a replacement for tests or review.

The repo is a bun workspace. The harness belongs to the root: `.claude/`, lefthook, CI, the root Biome config, and the root test suite (`bun run test:hooks`): the hook tests under `tests/hooks/` and the delegate runner's tests under `tests/scripts/`. Each package under `packages/` owns its source, tests, tsconfig and any Biome plugins in a nested `biome.json` that extends the root. Hooks resolve per package where it matters: typecheck-on-write checks the nearest `tsconfig.json`, guard-generated covers each package's `dist/` and `coverage/`, guard-boundaries applies only to `packages/cli/src/`, and project-status reads each package's `logs/*.jsonl`. `.claude/rules/architecture.md` and `.claude/rules/agent-ops.md` load in every session, and `.claude/rules/typescript.md` covers the TypeScript in `packages/cli/`, the root `tests/` and `scripts/`, and the hooks; the CLI-specific rules live in `.claude/rules/cli/` and are scoped to `packages/cli/`, and `.claude/rules/format/format.md` to `packages/format/`. A new package adds its own rules directory and, if it needs source boundaries, its own guard.

When extending the project, put a rule at the narrowest relevant path, add the behavior test first, and document new commands and debugging information in AGENTS.md. After changing hooks, rerun the hook suite and exercise one payload manually. Clean completed disposable worktrees after preserving unique source and deliverables.

## Repo hooks and shipped hooks

The repo's shell hooks (`.claude/hooks/*.sh`) correspond to the `agent-ops` fragment's `packages/cli/registry/fragments/agent-ops/files/.claude/hooks/` and `packages/cli/registry/fragments/agent-ops/adapters/claude/.claude/hooks/session-start.sh`. The shipped hooks were hardened for end users: a jq-free payload reader, `.env` write blocking, more destructive patterns and delegation to a TypeScript guard. The repo's `guard-commands.ts`, `guard-generated.ts` and `typecheck-on-write.ts` share names with different programs in `packages/cli/registry/fragments/claude-harness/adapters/claude/.claude/hooks/`.

These hooks are maintained separately. The repo's destructive guard is deliberately looser because the shipped patterns blocked legitimate agent work here. Do not port shipped hardening into `.claude/hooks/` unless a maintainer asks. `_lib.ts` and `_shell.ts` are the exception: they stay byte-identical with the `claude-harness` fragment's copies, checked by `tests/hooks/harness-sync.test.ts`.
