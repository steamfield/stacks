# Architecture

## Request path

gunicorn (`config/gunicorn.py`) loads `config.wsgi:application`. Middleware runs in the order
`config/settings.py::MIDDLEWARE` lists it:

1. `core.middleware.RequestLogMiddleware`: keeps a valid `X-Request-ID` or makes one, binds it to
   structlog's context, fills a missing `Cache-Control` with `no-store` (304s excepted), and logs
   one `request` line (method, route pattern, status, duration) after the response. `/healthz`
   logs at debug; 5xx at error.
2. Django's security middleware (HTTPS redirect, HSTS, nosniff), then whitenoise for the admin's
   `/static/` files.
3. Sessions, common (host validation), CSRF, auth, messages, clickjacking. DRF's views are exempt
   from CSRF; with no authentication classes there is no session to forge.

URLs: `config/urls.py` mounts each resource app under `/v1/`, plus `/healthz`, `/openapi.json`
and `/admin/`. Resource apps use DRF routers with path converters, so log routes read
`/v1/notes/<str:noteId>`.

## Errors

`core/errors.py::ERRORS` is the one table of tags, statuses, fixed messages and retryability.
`api_exception_handler` runs DRF's own handler (which turns `Http404` into a 404, adds
`WWW-Authenticate` and `Retry-After`, and rolls back an atomic request), then replaces the body
with `{"error": {"tag", "message", "retryable"}}`. Validation errors, malformed JSON, a wrong
method (with `Allow`), a non-JSON body (415) and an `Accept` the API can't meet (406) all go
through it. Outside DRF, `config/urls.py`'s `handler400`/`403`/`404`/`500` answer with the same
envelope: unknown paths, disallowed hosts, and any exception a view didn't expect, which
`django.request` logs once with its class and frames but not its message.

## Resources

`core/api.py` holds the bases: `ResourceSerializer` refuses undeclared fields,
`ResourceViewSet` refuses query parameters the action doesn't read and pages lists with
`CursorPage` (`?limit=&cursor=`, `{"items", "nextCursor"}`, newest first), and `ApiSchema`
documents the error envelope as every operation's default response. `notes/` is the example.

## Settings

`config/env.py::load` reads every deployment setting from the environment once, validates it and
fails startup with the variable's name. `DJANGO_ENV=production` turns DEBUG off, requires
`DJANGO_SECRET_KEY`, and turns on secure cookies, the HTTPS redirect (`/healthz` exempt), HSTS,
JSON logs and hashed static files. Everything else in `settings.py` is fixed code.

## Data

SQLite at `DJANGO_DB_PATH` (default `var/db.sqlite3`), in WAL mode with immediate transactions so
several gunicorn workers can write. Tests use a fresh test database per run (per xdist worker).
Migrations are generated by `makemigrations` and applied by `migrate`: `make dev` and `make start`
run it locally; a deployment runs it once as a release step before new code takes traffic.

## Logging

`config/logging.py` routes structlog and the standard library through one formatter: readable
lines in development, JSON lines on stdout in production. Exceptions keep class and frames but
never their message or local variables.

## Schema

drf-spectacular builds the OpenAPI document from the serializers and viewsets. `make openapi`
writes `openapi.json` (validated, warnings fail); `make check-openapi` fails when the committed
file no longer matches. The same document is served at `/openapi.json`.
