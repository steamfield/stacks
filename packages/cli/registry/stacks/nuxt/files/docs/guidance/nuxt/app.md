# Pages, components and data

## Where code goes

- `app/pages/` holds routes (file-based: `pages/notes/[id].vue` is `/notes/:id`). Each page has one root element.
- `app/layouts/default.vue` wraps every page through `<NuxtLayout>` in `app/app.vue`. A page picks another layout with `definePageMeta({ layout: "<name>" })`.
- `app/components/` holds components, auto-registered by file name (`AddNoteForm.vue` is `<AddNoteForm>`; `components/notes/List.vue` is `<NotesList>`).
- `app/composables/` and `app/utils/` are auto-imported too. Put a composable there when two pages share it.
- `app/error.vue` renders for any uncaught error, including unknown routes. It sits outside the layout.
- `shared/` holds code both app and server use (zod schemas, types), imported as `#shared/...`. It must not import from `app/` or `server/`.

## Auto-imports

Vue (`ref`, `computed`), Nuxt composables (`useFetch`, `useRuntimeConfig`, `useHead`, `createError`, `clearError`) and everything in `components/`, `composables/` and `utils/` are available without an import. Don't add explicit imports for them. `.nuxt/imports.d.ts` and `.nuxt/components.d.ts` list what is available; they're regenerated by `bunx nuxt prepare` (and `bun install`, `bun run typecheck`, the dev server). If a new composable or component shows as an unknown name in typecheck, run prepare before changing code.

Imports that aren't auto-imported (zod, `#shared/...`, types from packages) are written explicitly.

## Data fetching

- Read server data in a page with `await useFetch("/api/...", { key: "<name>" })`. It runs during server rendering and hands the result to the client, so the first paint has the data and the client doesn't fetch again.
- `useFetch` dedupes by key. After a write, call the `refresh()` it returned (the notes page does this when the form emits `added`); don't fetch again with a new key.
- Use `$fetch` for writes and user-triggered calls inside event handlers, never at the top of `<script setup>` (that runs twice, on the server and again on the client).
- Handle `error` from `useFetch` in the template with a safe message. The response type comes from the server route, so don't annotate it by hand.

## Forms

- The form posts JSON with `$fetch` and shows the field messages from the server's 400 `data.fields`. The server runs the same zod schema, so the form never repeats the rules. Add client-side checks only for feedback while typing, never instead of the server.
- Keep the label, `aria-invalid` and `aria-describedby` wiring: tests and screen readers find fields by them.
- Disable the submit button while pending, and clear errors on success.

## Runtime config in the app

`useRuntimeConfig().public` is the only config the app sees. Never read `process.env` in app code. Private keys exist only on the server.

## Errors

- Throw `createError({ statusCode: 404 })` in a page for a missing record so `error.vue` renders with that status.
- `error.vue` shows the status and fixed text, never `error.message`: production can carry server detail there. Its button calls `clearError({ redirect: "/" })`.
