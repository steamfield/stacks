# Bundled fragment audit

Status: IN PROGRESS 2026-10-31. Audit done; a devil's-advocate pass checked the plan against the code and its corrections are folded in below.

The goal is a fragment suite where adding any one fragment to a project lets a coding agent set up that capability well configured, following the tool's ecosystem conventions as they stand today, and proven by `stacks verify`. Fourteen of the 23 fragments need significant rework against that bar, and three CLI defects make every `add` worse than the matching `new`.

## Scope and evidence

All 23 fragments under `packages/cli/registry/fragments/` at `64a5ba6`, audited in seven families (agent-ops, repo tooling, release and deploy, databases, Effect, vendors, AI) against `packages/cli/skills/stacks-author/references/fragment.md`, `anatomy.md`, `.claude/rules/architecture.md` and each tool's current documentation (context7, vendor docs, `git ls-remote` for action tags). Every fragment's brief was composed with each stack its `applies_to` admits (`validate --brief`, default and sandbox), and installed for real with `new <stack> --with <id>` and with `add` into fresh stack scaffolds and hand-made dummy repos (bun/biome, Go/Makefile, Python/ruff).

Evidence levels: "reproduced" means a command was run and its output read (a hook fed a payload, a `goreleaser check`, a compose stack brought up, a Docker image built and run, a dummy repo carried through to `stacks verify`); "source" means the entry or CLI source shows the gap directly.

`bun run dev validate` reports 0 errors and 0 warnings today, so none of what follows is caught by the CLI.

## Cross-cutting findings

1. Verify proves little for most fragments (reproduced). Nine fragments have no verify step (ci-github, ce-plugin, clerk, effect, effect-schema, openrouter-ai, posthog, rest-api, cloudflare-pages), and several others have steps that pass while the capability is broken: agent-ops never runs a hook (a dummy repo went green in 0.0 s), git-hooks passes with `pre-commit: {}`, rr's `rr tasks` exits 0 on unknown keys, cloudflare-d1's verify runs `db:generate` and so writes the migrations it should be checking, postgres never runs a database test, goreleaser's `release-check` fails on every fresh project (no git remote).
2. Prose where files can ship (source, partly reproduced). Nine fragments ship nothing and the database fragments ship only docs. Working files were written and proved during the audit for git-hooks (commit-msg script and `lefthook.yml`), goreleaser (`.goreleaser.yaml` passing `check` and a six-target snapshot), docker-deploy (a 17 MB distroless go-api image, healthy), posthog (module, catalog and five tests with no key), the Postgres `compose.yaml` (both services healthy) and clerk's networkless verification.
3. `applies_to` admits stacks the body can't serve (source). effect and effect-schema admit five stacks with no Effect runtime (mobile-expo would get a third test runner, python-react's SPA has no loaders); claude-harness admits mobile-expo, python-react and pnpm projects where its verify step fails; rest-api's `api` tag admits stacks whose error envelope contradicts its rule; posthog admits three stacks it has no branch for, and its generic prose breaks each of them.
4. Stale ecosystem facts (reproduced against current docs and installed tools). ce-plugin routes to four skills ce 5.1.1 no longer ships; effect-otlp hand-parses env vars where Effect 4's `effect/observability` has `Otlp.layer`/`layerFromConfig`; docker-deploy's `workflow_run` publish lets a fork PR push to GHCR (security); cloudflare-pages puts `PUBLIC_*` build values in wrangler `vars`, which never reach the build; openrouter-ai asks agents to send the deprecated `usage.include`; posthog's consent default predates `cookieless_mode` and it never mentions `defaults`; goreleaser's Homebrew advice uses a deprecated hook.
5. Dead references (source). clerk names `test/clerk-mock.ts` and a `scripts/dev.sh --no-auth` path that the stack doesn't have; bun-release names `startStubReleases`, which exists only in openrouter-chat-cli; effect tells the agent to write a skill "in the skill tree AGENTS.md specifies", which no AGENTS.md specifies; openrouter-chat-cli's body contradicts its own eval checker's case ids.

## CLI and format findings

- C1, high, reproduced. `add` drops the host stack's `stacks:when with=<fragment>` blocks for the fragment being added, and those of already-applied fragments. `core/compose/compose.ts::compose` only includes the stack entry when `mode === "new"`, and `core/brief/render.ts::renderAddBrief` renders only `composition.fragments`. Lost in practice: go-api's Docker healthcheck note, astro-blog's "no server adapter" note for cloudflare-pages, python-react's "replace MemoryNotes" for postgres, cloudflare-react-router's test persistence note for D1, every stack's "the recipe already runs `lefthook install`" note (so the agent adds a second install step).
- C2, high, reproduced. `add` into a repo with no recorded stack (or a recorded stack the registry no longer has) has no tags (`compose.ts`: `tags: stack?.meta.tags ?? []`), so every `tag=` branch drops and every `tag!=` branch is included. ci-github loses all runtime guidance in exactly the existing-repo case.
- C3, medium-high, source. A fragment can't vary its shipped files by host stack: `stacks:when` resolves only in bodies, and `files/` lands at one path for every stack. This keeps posthog, docker-deploy, postgres, effect-sql-postgres and drizzle-postgres prose-only.
- C4, medium, reproduced. `add` into a sandbox project still tells the agent to ask the user about decisions: `core/add.ts` passes `yes: options.yes || options.sandbox` (the flag) rather than the resolved preset (`composition.preset`).
- C5, medium, reproduced. `stacks:when`/`stacks:end` markers inside shipped files (drizzle-postgres's `database.md` and `testing.md`) are copied verbatim, and validate doesn't say so. `stacks:fill` markers in shipped files are legitimate and stay.
- C6, low. Add briefs ask for `AGENTS.md` sections in repos that have no `AGENTS.md`. The `validate --brief` preview prints "found on PATH" for every tool without checking. The `conditional-dead-branch` note reads as "this branch is dead" when it means "this stack doesn't list the fragment". (The add brief keeps a fragment's H1 on purpose, per the comment in `renderAddBrief`; that stays.)
- C7, low. Validate has no note for a fragment with no verify step, or for two composed steps running the same command (openrouter-chat's `app-e2e` reruns the stack's `e2e`). Every composition check runs in `mode: "new"`, so add briefs (with a stack and with none) are never budget-checked or conditional-checked.

Out of scope, recorded for later: merging a fragment's `package.json` scripts into a templated stack `package.json`; conditional decisions; fragment `deps` naming a monorepo workspace; per-stack verify steps (a shipped test in the stack's test directory runs under the stack's own test step); generating the four adapter copies of a guidance doc from one source; recording a stack digest in the manifest so add can tell whether a stack note matches the project's version; a Workers static assets deploy fragment for astro-blog (Cloudflare now steers new projects to Workers; it would be a second permanent id for one stack and needs the maintainer's call).

## Decisions

- D1. Per-stack files use an overlay directory, `stacks/<stack-id>/`, inside a fragment, parallel to `adapters/<agent>/`: its files are planned only when `<stack-id>` is the composed stack (in add mode, the recorded stack), at the path after the prefix. Only fragments may have it. One function in `core/registry/entry.ts` maps an entry source path to its project path and its condition (agent or stack), and every site that hard-codes the `files|adapters` prefix uses it: `registry.ts::files`, `compose/plan-files.ts::fileWriters` (which gains the stack id), `show.ts`, `validate/submission.ts`, `validate/files.ts`, `validate/git.ts`, `validate/composed.ts`, `validate/compose-each.ts`, `validate/dated.ts`, `submit/body.ts`. Validate errors when the overlay stack doesn't exist or isn't admitted by `applies_to` (through `selection.ts::fitsStack`, ids or tags), and when an overlay path duplicates a `files/` path of the same fragment. Shipped-refs and imports run over every (fragment, overlay stack) composition, listed or not. Tag-keyed overlays are left out: a stack with several runtime tags would get colliding files.
- D2. With no recorded stack, or one the registry no longer has, `add` infers tags from the repo, reading data only (trust point 1): `Makefile` gives `make`; a `package.json` with `scripts` gives `scripts` only when there is no Makefile; `bun.lock`/`bun.lockb` or `packageManager: bun@` gives `bun`; `package.json` gives `node`; `tsconfig.json` gives `typescript`; `go.mod` gives `go`; `pyproject.toml` gives `python`; `Cargo.toml` gives `rust`; workspaces, or manifests in two or more immediate subdirectories, give `monorepo`. Inferred tags feed conditionals only: `applies_to` fit behaves exactly as today (tests in both directions). The add brief's header prints "Inferred tags: ..." so the agent can catch a wrong guess. Nothing is recorded in the manifest.
- D3. In add mode the brief renders, under each added fragment, the host stack's and the applied fragments' blocks whose `with=` condition names that fragment, headed as notes from that recipe's current version. An entry whose text is rendered this way counts in `composition.untrusted` when it's untrusted, so an untrusted shadowing stack can't reach launch or the picker (trust point 3). Stack notes that describe the stack's own files are written conditionally ("if `make install` already runs `lefthook install`, ..."), since an older project may predate them.
- D4. effect and effect-schema narrow to `applies_to: [effect]` (astro-fullstack, react-router, typescript-api, typescript-cli, the four stacks that already default to them). Ids stay.
- D5. claude-harness narrows to the stacks that list it, and its package-manager guard reads the lockfile instead of assuming bun. The TS guard allows `--force-with-lease`/`--force-if-includes`, matching what agent-ops already documents, and denies `git reset --hard <ref>` for any ref but `HEAD`.
- D6. cloudflare-pages stays on Pages with its fixes (build-time variables, redirects, the deploy trigger); a Workers static assets fragment is deferred (above).
- D7. docker-deploy and cloudflare-pages never use `workflow_run`. With ci-github, they publish from a job in the CI workflow (`needs:` the CI job, `if: github.event_name == 'push'`); without it, from their own workflow triggered by `push` to the default branch that runs the project's checks before publishing.
- D8. openrouter-ai's eval checker moves out of the vendor fragment into the two apps that run it (their `applies_to` lists are disjoint, so they never compose together). openrouter-ai ships its local stub server with a test and a verify step.
- D9. ci-github stays prose-only (a useful workflow is per-runtime, and action refs can't ship) and adds no required tool, since it's a default in all 14 stacks. Its verify step is a shell-only check that `.github/workflows/ci.yml` exists, defines `jobs:` and a `ci-ok` job, and holds no `stacks:fill`. actionlint and zizmor stay "run if installed" in the body.
- D10. git-hooks ships a language-neutral `.lefthook/commit-msg/conventional-commits.sh` and a `lefthook.yml` holding that job, plus a `stacks:fill` comment for pre-commit and pre-push. The Conventional Commits decision stays (default yes); declining it removes the job and the script. Verify runs the commit-msg script against a bad and a good message when the script exists, and checks through `lefthook dump` that pre-commit and pre-push each define a job with `run` or `script`.
- D11. Verify steps check; they never generate source. One line in `fragment.md` and `anatomy.md` (both copies: `packages/cli/skills/stacks-author/` and `packages/cli/plugin/skills/stacks-author/`).
- D12. ce-plugin maps `ce:fixing-flaky-tests` to `ce:writing-tests` and drops `ce:systematic-debugging`, `ce:optimizing-performance` and `ce:visualizing-with-mermaid`. The repo's own `.claude/rules/architecture.md` and `.claude/README.md` drop the same dead names.
- D13. Search cards: an entry edit restamps a reviewed card that still fits (`bun run decorate --restamp <id>`); no card is rewritten into a draft, because drafts are warnings that fail the gate. A card whose claims no longer fit is listed for the maintainer instead.

Rules for every B unit: load the `fragment-authoring` skill; read its family's audit report and treat every finding as in scope unless a decision overrides it; edit only its own fragment directories and their search cards; never edit a `STACK.md` or another unit's fragment, but return the exact stack edits it needs (I apply them, so the shared stack files have one writer); ignore validate findings in entries it doesn't own; keep ids; keep briefs inside the word budgets; run `bun run dev validate`, `bun run dev validate --brief <stack> --with <id> --sandbox` for each admitted stack, and `bun run test:unit tests/bundled-registry.test.ts tests/registry.test.ts tests/bundled-compositions.test.ts` from `packages/cli`. ## Done when

- `bun run dev validate` has 0 errors and 0 warnings; every fragment either has a verify step proving its own deliverable or a stated reason in its body why it can't.
- The QA installations reach `green`, with their findings fixed.
- The gate passes (`rr check`), the `code-reviewer` agent's findings on the whole diff are fixed, and the branch is merged to `main` locally (not pushed).

## Release impact

Changing agent-ops, git-hooks and ci-github changes the fingerprint of every stack's default composition, so every `runs.json` proof goes stale and `scripts/index/proof.ts` would publish those stacks as unproven. Most are already unproven or changed today (validate's ledger notes). The release runs from `origin/main`, which this local merge doesn't touch; before the next index redeploy, the maintainer benches the stacks (`bun run bench <stack>` per stack and preset) or releases from the commit before this merge.
