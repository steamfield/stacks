# Stack expansion research

The largest gaps are mainstream framework choice and API-only projects outside Effect. Add Next.js, SvelteKit, a FastAPI API and a Go API first, then Nuxt and a simple React SPA, then Django. Spring, Rails and Laravel wait for a format change: their package ecosystems (Maven, gems, Composer) aren't in `@steamfield/stacks-format`'s `Ecosystem`, so their `deps` can't be declared or allowlisted yet. The recommendations below are proposals for recipes, not claims that projects using these dependencies have already been built or benched. .NET is excluded at the maintainers' request.

## Evidence and assumptions

The registry currently has ten stacks: `astro-blog`, `astro-fullstack`, `cloudflare-react-router`, `go-cli`, `mobile-expo`, `python-react`, `react-router`, `tauri-react`, `typescript-api` and `typescript-cli`. React, Effect and TypeScript are well covered. Python requires a frontend, Go requires a CLI, and every standalone TypeScript API requires Effect. Vue, Svelte, PHP, Ruby and JVM have no base recipe.

Stack Overflow's 2026 web-framework question has 10,281 respondents. Missing technologies with substantial reported use include Next.js (20.6%), Vue (17.2%), Angular (16%), Spring Boot (12.8%) and Django (11.3%). FastAPI (18.5%) exists only inside `python-react`; Laravel, Rails, SvelteKit and Nuxt also appear in the survey. These are self-selected survey responses, not market shares. Priority here combines coverage, agent usefulness and maintenance cost, so it does not follow survey order. [Stack Overflow Developer Survey 2026, web technologies](https://survey.stackoverflow.co/2026/technology/data/web-framework)

Existing `python-react` already specifies structlog, OpenAPI generation and an app factory. Existing Effect stacks already specify structured logging. Reuse those conventions without requiring a frontend or replacing the logger. [The concurrent stack audit](../stack-audit-2026-10-29.md) proposes `dev-logs` extraction and records brief-budget pressure; do not add its code again under new ids.

All dependency lists below name **direct dependencies for the proposed scope**. Package managers resolve transitive dependencies and platform binaries into generated lockfiles. Do not copy an exhaustive transitive dependency tree into `deps`. Standard-library modules, SDK workloads, system packages, generator tools and services are listed separately. Resolve compatible versions at authoring time, then prove the generated project. Development-tool choices below are recommendations, not framework requirements.

All new stacks need agent-neutral guidance, README, `.env.example` when relevant, install/lint/typecheck/test commands, safe foreground server shutdown, and a meaningful proving slice. Artifact-producing stacks also need a real build and installed/built artifact proof. An unpackaged interpreted API such as the proposed FastAPI base is an explicit exception: its deliverable is the runnable source service, proven through HTTP, not a fabricated build target. Choosing a packaged API instead adds a build backend and wheel install proof. Existing `ci-github`, `git-hooks` and agent fragments need explicit language and task-runner branches before being advertised on new ecosystems. Do not apply the TypeScript-only `claude-harness` to Ruby or JVM projects by broad tags.

## First additions

### `nextjs` (P1): full-stack React on Node

- **Why:** Large uncovered framework; different routing, rendering, caching and build contracts from React Router justify a base recipe.
- **Runtime dependencies:** `next`, `react`, `react-dom`. Keep browser/server validation optional until a route needs it; choose `zod` then. No Effect dependency by default.
- **Development dependencies:** `typescript`, `@types/node`, `@types/react`, `@types/react-dom`, `eslint`, `eslint-config-next`, `vitest`, `@vitest/coverage-v8`, `@vitejs/plugin-react`, `jsdom`, `@testing-library/react`, `@testing-library/dom`, `@testing-library/jest-dom`, `@testing-library/user-event`, `@playwright/test`. For the proposed Tailwind default: `tailwindcss`, `@tailwindcss/postcss`, `postcss`. For formatting: `prettier`.
- **Tools/services:** Node LTS, Bun or npm with one consistent lockfile, Git; browser installed by Playwright. No external account or database.
- **Layout:** `src/app`, `src/components`, `src/lib/server`, `src/lib`, `tests`; App Router, server components by default, explicit client boundaries. A page reads a small server service and `/api/health` returns its result.
- **Proving slice:** a server-rendered list from an in-memory server service (`server-only` imports so it can't reach a client bundle), a form posting to a Server Action that validates input with `zod` and returns field errors, `revalidatePath` after a successful write, a route handler for health, and an error boundary. Tailwind is a decision with plain CSS modules as the fallback, not a fixed default. Run ESLint through its own CLI, since the framework's lint wrapper has changed between majors.
- **Verify:** lint, `tsc`, service/component tests, production build, production-server HTTP probe and browser navigation. Async server-component behavior belongs in browser/integration checks rather than pretending Vitest renders every server boundary.
- **Optional fragments:** database, auth, Sentry, OTel, Stripe, email, storage and deploy. Vercel deployment is optional; a working Node production build is the base.
- **Source:** [installation](https://nextjs.org/docs/app/getting-started/installation), [testing](https://nextjs.org/docs/app/guides/testing). Next's conventions and available test integrations should be checked against the installed release.

### `nuxt` (P1): Vue full-stack app

- **Runtime dependencies:** `nuxt`, `vue`, `vue-router`, matching the generated starter. Nitro and H3 are normally framework-managed transitive packages; declare them directly only if application imports require it.
- **Development dependencies:** `typescript`, `vue-tsc`, `@nuxt/test-utils`, `vitest`, `@vitest/coverage-v8`, `@vue/test-utils`, `happy-dom`, `@playwright/test`, `@nuxt/eslint`, `eslint`, `prettier`. Styling can start with ordinary CSS; Tailwind is optional rather than another framework integration in the base.
- **Tools/services:** Node, package manager, Git, Playwright browser; no hosted service.
- **Layout:** Current generated `app/` pages, components and composables; `server/api/health.get.ts`; server services separate from UI. Choose Node-server output and put runtime secrets in private runtime config.
- **Verify:** generated types plus `vue-tsc`/Nuxt typecheck, component tests in Nuxt's test environment, server route test, production build, `.output` server probe, browser navigation.
- **Optional fragments:** Pinia when cross-route client state is needed, Nuxt UI, auth, Postgres, observability, deployment. Avoid React-based UI fragments.
- **Sources:** [official starter dependencies](https://github.com/nuxt/starter/blob/v4/package.json), [Nuxt test utilities](https://github.com/nuxt/test-utils). The docs installation endpoint returned an unsupported Markdown response during this research; use the starter and current docs when authoring rather than assuming a directory/config version.

### `sveltekit` (P1): Svelte full-stack app on Node

- **Direct framework/build dependencies:** `svelte`, `@sveltejs/kit`, `@sveltejs/adapter-node`, `@sveltejs/vite-plugin-svelte`, `vite`; preserve the generated manifest's runtime/dev classification rather than inventing one. The adapter's emitted artifact controls runtime packaging.
- **Development dependencies:** `typescript`, `svelte-check`, `@types/node`, `vitest`, `@vitest/coverage-v8`, `@testing-library/svelte`, `@testing-library/jest-dom`, `jsdom`, `@playwright/test`, `eslint`, `@eslint/js`, `eslint-plugin-svelte`, `typescript-eslint`, `prettier`, `prettier-plugin-svelte`.
- **Tools/services:** Node, package manager, Git, Playwright browser. No database/account.
- **Layout:** `src/routes`, `src/lib/server`, `src/lib/components`, tests. Prove a server load, a form action with validation and a JSON health endpoint.
- **Verify:** framework sync/typecheck, lint, service/component tests, action validation test, Node adapter build and production probe, browser form submission.
- **Optional fragments:** database, auth, Sentry/OTel, Tailwind and deploy. Do not treat a static adapter as interchangeable with a server deployment when actions are present.
- **Sources:** [project creation](https://svelte.dev/docs/kit/creating-a-project), [Node adapter](https://svelte.dev/docs/kit/adapter-node). Current docs describe config changes across framework generations; generate config from current docs instead of shipping frozen `svelte.config.js` assumptions.

### `python-api` (P1): FastAPI service without a frontend

The id follows `typescript-api` and `go-api`; the name, description and search card say FastAPI so "fastapi" requests find it.

- **Runtime dependencies:** `fastapi`, `uvicorn`, `pydantic`, `pydantic-settings`, `structlog`.
- **Development dependencies:** `ruff`, `mypy`, `pytest`, `pytest-asyncio`, `pytest-cov`, `pytest-xdist`, `pytest-randomly`, `httpx`, `asgi-lifespan`. Add `respx` only when testing outbound HTTP rather than requiring it for health.
- **Tools/services:** Python, uv, Make, Git; no Node or Docker in the base.
- **Layout:** Reuse `python-react`'s `app/` factory, settings, lifespan, routers, schemas, services and error envelope as a root API project; preserve dependency overrides and import-without-network guarantees. Commit generated `openapi.json` and provide a drift check.
- **Verify:** ruff, mypy, pytest with real ASGI transport/lifespan, schema/envelope tests, spec drift, Uvicorn serve probe and wheel/build only if the project is deliberately packaged. No fake build command for an unpackaged app.
- **Optional fragments:** `postgres` widened to this id (SQLAlchemy/Alembic, same harness as `python-react`), `docker-deploy` if its Python branch fits a root-level project, `ci-github` and `git-hooks` through their Python branches. Sentry/OTel come in Batch 2; auth and Celery later. Do not add the frontend's client-generation packages.
- **Proving slice:** one resource with create/list (in memory without `postgres`), request validation errors in the shared envelope, a dependency failure mapped to 503 through a dependency override, request-id middleware and structlog JSON lines.
- **Sources:** [FastAPI tutorial and installed dependencies](https://fastapi.tiangolo.com/tutorial/), [uv project conventions](https://docs.astral.sh/uv/guides/projects/).

### `go-api` (P1): Go HTTP service

- **Runtime dependencies:** Prefer standard-library `net/http`, `encoding/json`, `log/slog`, `context`, `os/signal`, `errors` and `time`; no router package is required for a small API. If named-framework demand wins, make `gin-api` a separate later recipe using `github.com/gin-gonic/gin`, rather than silently calling Gin a standard Go service.
- **Development dependencies/tools:** Go test, `net/http/httptest`, race detector, `go vet`, `gofmt`; `github.com/stretchr/testify` only if matching the current Go CLI assertion style. `golangci-lint` and `golang.org/x/vuln/cmd/govulncheck` are tools, not runtime libraries. Make, Git and Go toolchain.
- **Layout:** `cmd/server`, `internal/{httpapi,config,service}`, `tests`; small handler/service seam, structured slog request logging, explicit error responses, body limit, server timeouts and graceful shutdown. Default no persistence.
- **Verify:** fmt/vet/lint, tests with race detection, built binary, health and invalid-body tests through a real HTTP server, serve probe and signal shutdown. Prove routing/method semantics rather than only a health function.
- **Optional fragments:** `ci-github` and `git-hooks` through their Go branches; `docker-deploy` only if it gains a Go branch. `goreleaser` does not fit: its body builds a CLI with `--version` ldflags, and its `applies_to` is narrowed to `go-cli` in Batch 0. PostgreSQL with `github.com/jackc/pgx/v5`, OTel (Batch 4) and auth later; Prometheus deferred.
- **Proving slice:** a small in-memory resource with `GET` list, `GET` by id, `POST` with JSON validation, method-not-allowed and not-found responses using Go 1.22+ `ServeMux` method patterns, a JSON error envelope, request-id and slog access-log middleware, `http.MaxBytesReader`, and `Server.Shutdown` on SIGINT/SIGTERM with a bounded timeout.
- **Source:** [Go's official REST tutorial](https://go.dev/doc/tutorial/web-service-gin) demonstrates Gin as an alternative, not evidence that Gin is mandatory. The standard library is the minimal proposed default.

## Second wave

### `django` (P2): Python server-rendered app

- **Runtime:** `django`, `gunicorn`, `whitenoise`; SQLite from Python's standard library for the default local database. Built-in Django templates, ORM, sessions, authentication and admin are part of the framework, not extra package dependencies.
- **Development:** `ruff`, `mypy`, `django-stubs` with its plugin, `pytest`, `pytest-django`, `pytest-cov`, `djlint`; optional browser check uses Python `playwright`, `pytest-playwright`. Tools: Python, uv, Make, Git; no JavaScript toolchain unless selected UI needs one.
- **Layout/proof:** `config/`, one feature app, templates/static, migrations and tests; health plus a tiny model rendered in a page. Verify migration creation has no drift, migrations on a disposable database, Django checks, lint/types/tests, collectstatic, HTTP serve and browser proof. Production config check uses test secrets/settings rather than user credentials.
- **Fragments:** Postgres (`psycopg`), HTMX (`django-htmx` plus vendored or installed `htmx.org` as the actual browser asset), DRF (`djangorestframework`, `drf-spectacular`), Celery and deploy. API capability is a fragment unless the layout changes substantially.
- **Source:** [Django tutorial](https://docs.djangoproject.com/en/5.2/intro/tutorial01/) establishes framework project/app/admin conventions; author against the supported release chosen then.

### `react-vite` (P2): browser-only React SPA

- **Runtime:** `react`, `react-dom`, `react-router`, `@tanstack/react-query`. Avoid Effect and backend dependencies; add `zod` only if the proving slice validates external data.
- **Development:** `vite`, `@vitejs/plugin-react`, `typescript`, `@types/node`, `@types/react`, `@types/react-dom`, `@biomejs/biome`, `vitest`, `@vitest/coverage-v8`, `happy-dom`, `@testing-library/react`, `@testing-library/dom`, `@testing-library/jest-dom`, `@testing-library/user-event`, `msw`, `@playwright/test`. Optional Tailwind: `tailwindcss`, `@tailwindcss/vite`.
- **Tools/layout:** Node, package manager, Git; `src/app`, routes, components, API boundary; tests use MSW and the real fetch boundary.
- **Verify:** lint/types/tests, static build, preview probe and browser deep-link reload. One routed view with success/error states, not a backend stub pretending to be an API. No server-secret environment variables in the bundle.
- **Fragments:** external API contract, auth client, PostHog, Sentry browser, static deploy, UI tools. This fills a separate product type from SSR React Router and two-runtime Python React.
- **Source:** [Vite guide](https://vite.dev/guide/).

### Deferred: Spring Boot, Rails and Laravel

The three outlines below stay as research. They are deferred until `Ecosystem` and `core/deps.ts::readDependencies` cover Maven, gems and Composer (a `@steamfield/stacks-format` release), and `ci-github`/`git-hooks` gain JVM, Ruby and PHP branches.

### `spring-boot-api` (deferred): Java REST service

- **Runtime/build coordinates:** Spring Boot parent/BOM and plugin; choose the current Initializr Spring Web starter (older projects use `org.springframework.boot:spring-boot-starter-web`; resolve the current artifact rather than freezing that assumption), validation starter and actuator starter. Jackson and logging implementation should come from the starter, not manually pinned transitive jars.
- **Development:** current Boot test starter; JUnit and mocking supplied by its test platform; Maven Surefire/FailSafe, JaCoCo and Spotless Maven plugins. Use the generated Maven wrapper and Java toolchain.
- **Layout/proof:** `src/main/java/<package>/{api,service,config}`, resources and parallel test tree; typed DTO, bean validation and one health/business response. Verify formatter, Maven tests, startup/config failures, packaged executable jar and HTTP probe. No JPA or database in the base.
- **Fragments:** JPA/Postgres (Boot data-JPA starter, `org.postgresql:postgresql`, Flyway), security, Testcontainers and Micrometer/OTel.
- **Source:** [Spring's REST service guide](https://spring.io/guides/gs/rest-service/) and current Initializr metadata during implementation.

### `rails` (deferred): Ruby server-rendered app

- **Runtime:** generator-resolved `rails`, `puma`, `sqlite3`, `propshaft`, `importmap-rails`, `turbo-rails`, `stimulus-rails`, `jbuilder`; `bootsnap` and platform `tzinfo-data` when the generated app requires them. Framework generation decides current direct defaults. Avoid adding a Node toolchain to importmap mode.
- **Development/test:** framework Minitest; `capybara`, `selenium-webdriver` for system tests; `rubocop-rails-omakase`, `brakeman`, `bundler-audit`, `debug`, `web-console` as appropriate development groups.
- **Tools/layout/proof:** Ruby, Bundler, SQLite/system build headers, Git, browser; normal Rails directories and one model/controller/view proving slice. Verify formatter/security commands, tests, migrations on owned temporary database, assets precompile, system test and server health. Add a minimal runtime assertion in place of claiming Ruby has a typecheck by default.
- **Fragments:** Postgres (`pg`), jobs (current generated Solid Queue dependencies or Sidekiq), auth generator, billing and deploy. Do not force Solid Cache/Cable/Queue into a recipe that does not use them simply because a generator can install them.
- **Sources:** [Rails guide](https://guides.rubyonrails.org/getting_started.html), [official generated Gemfile template](https://github.com/rails/rails/blob/main/railties/lib/rails/generators/rails/app/templates/Gemfile.tt).

### `laravel` (deferred): PHP server-rendered app

- **Runtime:** `laravel/framework`, `laravel/tinker`; PHP extensions from the selected release (not Composer dependencies), PDO SQLite initially. Blade in the base. Composer's framework dependency brings most Illuminate components transitively.
- **Development:** `fakerphp/faker`, `laravel/pint`, `mockery/mockery`, `nunomaduro/collision`, `phpunit/phpunit`, plus `larastan/larastan` for static analysis. Generated development tools such as Pail/Pao can be kept if the recipe uses them. Frontend build only when generated assets require it: `vite`, `laravel-vite-plugin`, `tailwindcss`, `@tailwindcss/vite`, `concurrently`.
- **Tools/layout/proof:** PHP, Composer, SQLite extensions, Git and Node/package manager if assets are compiled; standard app/routes/resources/database/tests. Verify Pint, PHPStan, PHPUnit feature tests, isolated migrations, asset build if present, cached-config boot and HTTP probe. Set an ephemeral app key for tests; never use production `.env`.
- **Fragments:** Inertia/React (`inertiajs/inertia-laravel`, `@inertiajs/react`, React and corresponding build/types), Livewire (`livewire/livewire`), Sanctum, Redis/Horizon, billing and deploy. Pick Blade initially rather than installing three UI approaches together.
- **Sources:** [installation](https://laravel.com/docs/12.x/installation) (redirect to the current release before authoring), [current skeleton Composer dependencies](https://github.com/laravel/laravel/blob/13.x/composer.json).

## Fragment fit for Batch 1 stacks

After Batch 0 narrows the framework-specific lists, a new stack fits the universal fragments (`agent-ops`, `ce-plugin`, `ci-github`, `git-hooks`, `rr`), `rest-api` if tagged `api`, `claude-harness` if tagged `node` or `bun`, plus whatever its author admits by id. Each Batch 1 stack author checks `ci-github` and `git-hooks` have a branch for the stack's language and task runner, and decides per fragment whether to admit `claude-harness` (Node/Bun stacks only), `effect`/`effect-schema` (no: the new stacks don't use Effect), `posthog` (no, until its Batch 2 revision adds a branch), `docker-deploy` and `rest-api` (only if their bodies already cover the layout), composing each one admitted.

## Deliberate deferrals

- **Express, Flask and Gin:** Recognized names, but adding all of them immediately multiplies API recipes before proving demand. Hono/Nest, FastAPI/Django and standard Go give more distinct starting points. If requested later, Express runtime is `express` with `zod`, dev `@types/express` plus the Hono Node tool set and Supertest; Flask runtime is `flask`, `gunicorn`, `pydantic-settings`, dev the Python test/tool set; Gin uses `github.com/gin-gonic/gin` with the Go test/tools above. Each needs health, request validation, error envelopes, runtime logging and a real serve/build proof.
- **WordPress:** Survey presence does not alone make it a good agent-first greenfield recipe. A future scope must choose theme versus plugin, local PHP/MySQL/container lifecycle, and WordPress integration testing. Runtime WordPress/PHP/MySQL; theme tooling differs from plugin dependencies, so a generic one-id proposal would hide the actual contract.
- **Kubernetes, Terraform, AWS CDK and Pulumi:** These are infrastructure fragments or separate infrastructure project types, not synonyms for an app stack. Define account-free validation and explicit apply boundaries before planning them as launch additions.
- **Training/inference stacks:** Do not ship a generic “AI/ML stack” that silently installs CUDA/PyTorch and requires model downloads. Start with deterministic CPU data work; propose named inference/training runtimes once platform, artifact size, offline fixture and hardware requirements are explicit.
- **More React combinations:** Existing React Router, Astro, Expo and Tauri already cover several React surfaces. A database, auth vendor or hosting choice usually belongs in a fragment rather than a new stack named after every combination.

## Authoring sequence

1. Prototype the P1 choices from empty directories, resolve dependencies from official generators/docs, record blockers, and choose the minimal defaults before creating registry entries.
2. Build language/runtime support in reusable fragments when a new stack needs it. Keep logger frameworks native to their host. New tags must not accidentally admit unrelated fragments.
3. Write stack/search drafts under the existing authoring skills, with agent-neutral guidance and exact direct dependency lists for reachable branches. Keep each default brief under its budget; link durable long guidance rather than embedding it all.
4. Validate registry references and each supported composition, exercise realistic winning and sibling search requests, and obtain a fresh bench proof for the new recipe. No proposal above is proven by documentation research.
5. Add a new ecosystem only when CI/agent hooks can run its real checks. A nominal entry with no build or served deliverable proof does not close the gap.
