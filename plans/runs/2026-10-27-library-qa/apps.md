# CLI app QA and initial React Router attempt

The packed `@steamfield/stacks` 0.3.1 CLI from commit `02a8554ebed597c554107468fdf73d2ea7907f41` ran under Node 24.21.0 with isolated XDG, data and state directories. The host was macOS arm64 with Bun 1.4.2 and lefthook 2.1.17. The final CLI app used Effect/OpenRouter 4.0.7, OpenTUI 0.7.0, TypeScript 5.9.3 and Vitest 5.0.5. No paid provider request or credentials were used. Model choice was `openai/gpt-4.1-nano` for the live default, with a disposable local model and key for tests.

The initial verification failures for both bases were expected: `stacks new` says it installs nothing and does not create `package.json`. They are not counted as CLI defects. The final CLI app checks are green, but this run's application has concrete implementation gaps. The model picker rendered a selection control, but it had no search input or filtering; choosing a different model was not directly tested. The eval printed model, case, pass/fail, elapsed milliseconds and a total pass count; it did not print finish reason, token counts, cost, actual served model, per-model median latency, or write timestamped result files. Its scoring was inline rather than a separately tested pure scorer, and it did not impose a per-case deadline. These are omissions in this temporary implementation, not established defects in the recipe. The manifest's TUI smoke checks that the picker opens and closes, not search; the eval step checks dry-run success, not the completeness of its report, so both steps passed despite those omissions.

Separately, comprehensive terminal state coverage, the full upstream-status matrix and exact schema-wire assertions were not audited; lack of those tests alone does not establish a broken feature. The recording script was authored but not exercised against a paid provider; no real fixture was fabricated. The replay skip therefore limits provider compatibility conclusions. The stub eval tests execution and scoring plumbing, not model quality. Tests and the manifest were not weakened to reach green.

## Findings

### P2: Added app file needs formatting under the prescribed base configuration

Expected: after a clean base and app addition, shipped app files should conform to the base brief's Biome configuration. Observed: the first composed verify failed lint on `scripts/lib/stub-pid.ts`, where the conditional spread did not match Biome 2.6.3 at the prescribed 100-column width. The base failure caused all five app steps to be skipped: 12 passed, 1 failed, 5 skipped. Recovery: run the project's normal formatter and rerun verify. Owner: `openrouter-chat-cli` shipped file and library validation. Reproduce by creating and completing a `typescript-cli` base with the sandbox preset, then running `<cli> add openrouter-chat-cli --json --no-launch` and `<cli> verify --all --json` from that project. This is a generated-file formatting issue, not a provider failure.

### P2: Codex-only app guidance names rules that were not supplied

Expected: references in the add brief and its shipped docs should lead to guidance present for the selected adapter. Observed: the brief asks the agent to read app rules, and `docs/ask-turn.md` names `tui.md`, `cli.md`, `effect-ai.md` and `openrouter.md`; the Codex-only project contains no `.claude/rules/` directory. The portable `.agents/skills/openrouter-chat-cli/SKILL.md`, `DESIGN.md` and `docs/ask-turn.md` provide much of the substantive guidance, so this is not a claim that the whole recipe is absent. Recovery: use those available files and installed package declarations. Owner: app guidance and adapter composition. Reproduce with `<cli> new typescript-cli <qa-root>/cli --sandbox --agents codex --json --no-launch`, then add the app after the base is green and inspect the named paths.

### P2: A fresh Effect skill is required before it exists

Expected: an agent can follow the installed skill's lookup order before writing code. Observed: the shipped Effect development skill directs it to load a separate project Effect skill before writing Effect code, while the brief directs it to create that skill after core compilation. No separate skill exists in a fresh scaffold. Recovery: use installed declarations to build the initial slice and write the skill after compilation. Owner: Effect fragment guidance and agent-ops instructions. This applied to both bases.

### P2: First-test timing can reflect a step that ran no tests

Expected: a first-test-pass timestamp used as a benchmark should identify an actual test pass or clearly disclose the proxy. Observed: in the initial web attempt, the first passing test-layer step was `harness-hooks`, whose command succeeds when `tests/hooks` is absent; the main test script had failed. The state nevertheless recorded `firstTestPassAt`. Recovery: inspect the named step and runner counts before reporting a benchmark. Owner: run-state timing/verification reporting. Reproduce with a freshly scaffolded base after installing a generator and before creating `tests/hooks`, then inspect `<qa-root>/state/projects/` and the verify result.

### P3: Repository command guard also intercepted unrelated scratch-project tests

Expected: this independent project can run its own scoped Bun test or test script. Observed: the parent repository's PreToolUse command guard blocked `bun run test`, `bun run test:unit` and a scoped `bun test ./tests/tui/app.test.tsx` from the temporary project, citing the parent clone's rr policy. `stacks verify`, scoped Node Vitest runs and `bun run test:tui` did run. Recovery: use the packed CLI's verify and a permitted project-specific test script. Owner: repository harness command guard, not the stacks CLI.

## Integration observations

OpenTUI 0.7.0's `bun-ffi-structs` dependency declares a TypeScript `^5` peer; adding it to a TypeScript 7 base produced Bun's peer warning. TypeScript 5.9.3 satisfied that peer and passed the checks. The real Effect/OpenRouter provider classified a scripted HTTP 402 as a non-retryable unknown error, so the temporary app explicitly mapped 402 to retryable credits guidance; a test proved three attempts and the safe message. On MCP stdin EOF, serving directly in the parent scope exited 1 with `All fibers interrupted without error`. Running the server in a child fiber and treating an interruption-only child exit as normal produced exit 0 and returned the in-flight tool response. These are observed integration behaviors with local workarounds, not by themselves stacks CLI defects.

The actual verify results are in [apps-evidence](apps-evidence/), with sanitized manual excerpts. No source, registry, ledger or shared configuration was changed and no commit was made.
