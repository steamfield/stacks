## Finding: Astro check can report success without running a check

Severity: moderate DX/verification gap; ownership: Astro blog recipe and upstream Astro command behavior, not a demonstrated CLI execution defect. Reproduction: generate the minimal Astro 7.4.2 project without installing `@astrojs/check` or TypeScript, then run the shipped `make check` in a noninteractive shell. It printed a prompt to install `@astrojs/check typescript`, then exited 0. The preliminary `stacks verify --json` consequently marked `check` passed. Expected: the check either runs or exits nonzero when its required dependency is absent. The brief explicitly instructs installing both dependencies, so this occurred during incomplete setup, not a complete compliant project. The transcript is in [astro-blog-check-prompt.txt](web-api-evidence/astro-blog-check-prompt.txt). Recovery was not tested; installing the dependencies is the brief's intended setup.

## Finding: Codex-only API briefs reference missing rules

Severity: moderate agent guidance gap; ownership: `typescript-api` and `astro-api` recipes/adapters. Reproduce with `<cli> new typescript-api <qa-root>/api --sandbox --agents codex --json --no-launch`, then read `.stacks/BRIEF.md` and list `.claude/rules/`. The brief directs the agent to `.claude/rules/src/effect-api.md` and `.claude/rules/src/testing.md`, but the Codex-only scaffold has no `.claude/rules/` directory. The Effect development skill is a workflow stub that directs the agent to create a separate installed-API skill, not a copy of these detailed rules. `astro-api` likewise names `.claude/rules/api/effect-api.md`, `.claude/rules/api/testing.md`, and `.claude/rules/web/astro.md` absent from its Codex-only scaffold. Expected: the named instructions exist for the selected adapter or the brief links equivalent material that does. Recovery for the TypeScript run was to inspect installed Effect 4 declarations and examples, and generate an installed-API skill; this does not recover the omitted stack-specific rules. The same absence was confirmed in the adapter sources.

## Finding: Astro preview also backgrounds under an agent

Severity: low DX friction; ownership: Astro blog recipe guidance and upstream Astro behavior. With Astro 7.4.2 and the generated `make preview`, running the target under this agent returned immediately after starting a background preview process. The brief warns about the corresponding `astro dev` behavior and its `--ignore-lock` workaround but does not mention preview. Expected: the preview target's background behavior and cleanup are clear to an agent. Astro printed `astro preview stop`; running `bunx astro preview stop` stopped the owned server, and its port was clear. No CLI defect is demonstrated.

## Other observations

- The Cloudflare generator completed without deploying. Its underlying React Router generator included an agent skill even though create-cloudflare was called with `--no-agents`; the skill was not copied into the scaffold. This is generator behavior, not an established stacks defect.
- The first Cloudflare dev attempt failed because this run omitted the generator's two referenced TypeScript configs during its manual merge. Copying them fixed startup; this was an implementation error.
- In the TypeScript implementation, the first genuine query decode test returned 500 because Effect 4 raises `HttpApiSchemaError` as a defect. Inspecting its installed type and distinguishing request decode from response encoding fixed it to 400. The first manual log query showed duplicate terminal records and an undefined duration; matching the shipped wrapper's documented line format and `durationMs` field fixed both. These were implementation mistakes, not established recipe defects.
- Astro's current checker 0.9.12 declared TypeScript 5 or 6 peers; the first install of TypeScript 7 produced peer warnings. Installing TypeScript 6.0.3 resolved them, as the brief's gotcha suggests. Effect packages resolved together to 4.0.7, Astro 7.4.2, React 19.3.1, Vitest 5.0.5 and Biome 2.6.3.
- Cloudflare's generator selected React Router 8.5.1, Wrangler 4.154.0, Vite 8.3.5 and TypeScript 5.9.3. The installed Workers plugin was `@cloudflare/vitest-plugin` 1.4.9 with Vitest 5.0.5; Cloudflare's current docs specify Istanbul because native V8 coverage is unsupported. A test using a mocked rejected work function failed in the Workers pool even when the rejection was caught; an ordinary rejected-promise probe passed. Replacing the mock with a directly injected async work function let the test assert the actual propagated error. This is a test setup observation, not a confirmed upstream defect. The [first failure](web-api-evidence/cloudflare-test1.txt) and [recovery](web-api-evidence/cloudflare-test2.txt) are retained.
- These preliminary failures reflect unfinished agent work and an occupied port, not proof that the stack recipes are broken. No conclusions can be drawn about complete setup time or final verify iteration counts.
